# Research scripts

Standalone evaluation scripts backing the claims in the root [README](../README.md)
and [RESEARCH.md](../RESEARCH.md). None of these are part of the installed
`asterism` package or touch your real `~/.asterism/asterism.db` — each seeds
its own throwaway, isolated SQLite file and deletes it when done.

Run any of them from the repo root (or anywhere — they locate the repo root
themselves):

```bash
python research/poc_compare_v2.py      # the current, corrected single-model eval
python research/poc_compare.py         # superseded first attempt, kept for the audit trail
python research/benchmark_latency.py   # local-only, no API calls
python research/poc_compare_multimodel.py <model> [n_runs]   # cross-model eval, see below
```

| Script | What it measures | Needs API key? |
|---|---|---|
| `poc_compare_v2.py` | Does graph-injected retrieval commit to a specific answer more often than a flat, unweighted list of the same facts (`flat_list`), or no memory at all (`none`)? Corrected scorer, validated against a held-out set *before* the live run. Single assistant model (`claude-sonnet-4-6`). | Yes |
| `poc_compare.py` | The original attempt at the same question. Superseded by v2 (regex bug + a category-mismatched metric on descriptive queries) — kept, not deleted, so the correction is auditable rather than quietly overwritten. | Yes |
| `poc_compare_multimodel.py` | The same eval, same fixed graph/queries/conditions/scorer, but with the **assistant model** as the only thing that varies — see below. | Yes (Anthropic or OpenAI, depending on model) |
| `benchmark_latency.py` | Does graph retrieval latency scale acceptably as the graph grows (100 / 1,000 / 10,000 synthetic nodes)? | No |

## Reproducing the cross-model eval

`poc_compare_multimodel.py` reuses `poc_compare_v2.py`'s scorer, held-out
`VALIDATION_SET`, and `validate()` **unchanged** — imported, not copied,
never re-tuned. Only the assistant model varies; the seeded graph, the 12
PRIORITY queries, the 3 inject conditions, and the scoring rule are all
identical to the v2 eval. `extract_triples()`'s own model (graph
maintenance, Haiku/local Ollama) is independent of this and unaffected.

A single 36-call run is a small, noisy sample — response phrasing (and so
the deterministic scorer's label) varies run to run even for the same
model. Rather than chase a single-run number, the script runs the full
36-call eval `n_runs` times per model (each against a freshly reseeded
isolated DB, never touching your real `~/.asterism/asterism.db`) and
reports the across-run distribution — mean/min/max per condition, and the
graph-vs-flat_list gap per run. There is no target to hit; whatever the
distribution is gets reported.

```bash
python research/poc_compare_multimodel.py claude-sonnet-4-6 5   # needs ANTHROPIC_API_KEY
python research/poc_compare_multimodel.py claude-opus-4-8 5     # needs ANTHROPIC_API_KEY
python research/poc_compare_multimodel.py gpt-5.5-2026-04-23 5  # needs OPENAI_API_KEY
```

Model strings starting with `gpt`/`o1`/`o3`/`o4` route to OpenAI
(`chat.completions.create`); everything else routes to Anthropic. Copy
`.env.example` to `.env` and fill in whichever key(s) the models you're
running need — see the root README's Privacy section for what does and
doesn't leave your machine.

## results/

Generated output from the scripts above — full side-by-side responses,
scored commit/hedge tables with per-query labels, and latency numbers.
Regenerated by re-running the corresponding script; not hand-edited.

- `poc_eval_results_v2.md` — single-model (sonnet) quantitative result
- `poc_results_v2.md` / `.json` — full response text backing it
- `poc_eval_results.md`, `poc_results.md` / `.json` — superseded v1 attempt, kept for the record
- `benchmark_results.md` — latency numbers
- `poc_eval_results_<model-tag>_aggregate.md` — cross-model result: mean/min/max commit rate and gap distribution across runs, one per model
- `poc_results_<model-tag>_run<i>.md` / `.json`, `poc_eval_results_<model-tag>_run<i>.md` — per-run detail backing each model's aggregate
